# 第2週: 指示の出し方の基本

## 今週のゴール

サイトの見た目（色・文言）を、自分の言葉で Claude に頼んで変えられる。
「計画を見てから進めてもらう」流れに慣れる。

## 1. 今週の教材を Claude に読んでもらう

Codespaces を開き、ターミナルで `claude` を起動して、こう頼みます。

```
docs/week02.md を読んで、今週やることを短く教えて
```

## 2. まず小さく変えてみる

次の指示を、そのまま送ってみましょう。

```
トップページの大きな見出し「次の休みは、どこへ行こう。」を
「週末、ちょっと遠くへ。」に変えたい。
変える前に、どのファイルをどう変えるか教えて。
```

Claude が計画を見せてくれたら、内容を読んで「それでお願いします」と返します。
プレビューを再読み込みして、見出しが変わっていれば成功です。

> Claude は作業を始めるとき「ブランチを作ります」と言うことがあります。ブランチは「本番に影響しない作業用の枝」です。詳しくは第3週で扱います。

## 3. 自分で考えて頼む（今週の課題）

次のうち2つ以上を、**自分の言葉で**頼んでください。指示文は提出で使うので、メモしておきましょう。

- サイト全体のメインの色を変える
- ボタンの文字や形を変える
- トップページに「このサイトについて」の短い紹介文を足す
- フッターの文言を変える

指示を出すときは [README のよい指示の4つのポイント](README.md#よい指示の4つのポイント) を見返してください。

## 4. 思い通りにならなかったら

一度でうまくいかないのは普通です。違いを具体的に伝えましょう。

| 思ったのと違ったとき | 言い直しの例 |
| --- | --- |
| 色が濃すぎた | 「もう少し明るい緑にして。今の色より2段階くらい薄く」 |
| 変えてほしくない所まで変わった | 「ヘッダーの色は元に戻して。ボタンだけ変えたい」 |
| 何が変わったか分からない | 「さっきの変更で、画面のどこが変わったか教えて」 |

## 5. 保存して push する

作業の最後に、こう頼みます。

```
今日の変更をコミットして push して
```

コミットは「変更をセーブすること」、push は「セーブした内容を GitHub に送ること」です。

## 6. 提出する

第2週から PR で提出します。Claude に次のように頼んでください。

```
今週の変更で PR を作って
```

PR ができたら、GitHub で PR を開き、本文の4つの欄を自分で書きます。
しばらくすると Vercel が PR にコメントを付け、**プレビュー URL**（本番とは別の確認用 URL）が表示されます。その URL を「結果」欄に貼ってください。

今週はまだ**マージ（本番への反映）はしないで**ください。第3週で行います。

## 今週わかったこと

| 言葉 | 意味 |
| --- | --- |
| ブランチ | 本番に影響しない作業用の枝 |
| コミット | 変更をセーブすること |
| push | セーブした内容を GitHub に送ること |
| PR | 「この変更を本番に入れていいですか」という確認依頼 |
| プレビュー URL | PR の内容だけを試せる、確認用のサイト |
